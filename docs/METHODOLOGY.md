# Methodology: Profanity -> Wintermute 2 Attack Path

This document derives the complete mathematical path from Profanity's `createSeed()` function to the Ethereum address that was exploited in the Wintermute 2 incident.

---

## 1. Profanity's createSeed()

Profanity generates a 256-bit private key with the following logic (simplified):

```cpp
cl_ulong Profanity::createSeed() {
    std::random_device rd;
    std::mt19937_64 rng(rd());          // 32-bit seed -> 64-bit PRNG
    std::uniform_int_distribution<cl_ulong> dist(0, UINT64_MAX);
    
    cl_ulong r0 = dist(rng);
    cl_ulong r1 = dist(rng);
    cl_ulong r2 = dist(rng);
    cl_ulong r3 = dist(rng);
    
    return r0 | (r1 << 64) | (r2 << 128) | (r3 << 192);
}
```

The vulnerability is immediately visible:
- `rd()` returns a **32-bit value** (on most platforms, `std::random_device` is backed by `/dev/urandom` but Profanity casts it to `uint32_t` implicitly via the MT19937_64 constructor).
- This 32-bit value seeds a **2^19937-1 period** PRNG, but the **key space is only 2^32**.

## 2. Seed -> Private Key Mapping

Given a 32-bit seed `s`:

```
MT19937_64(s) -> [r0, r1, r2, r3]   (each r_i is a 64-bit uint)
private_key_seed = r0 || r1 || r2 || r3   (256-bit concatenation)
```

Profanity then scans iterators:
```
for i in [0, MAX_ITER]:
    private_key = private_key_seed + i
    address = derive_address(private_key)
    if address matches vanity_pattern:
        return (private_key, address)
```

Typical `MAX_ITER` is ~2,000,000 (2M) to find a 7-char vanity prefix.

## 3. The Attack

From the **public key** of the victim address, the attacker can:

1. Enumerate all 2^32 possible seeds.
2. For each seed, compute `private_key_seed`.
3. Derive the corresponding public key `P_seed = private_key_seed x G`.
4. Check if `P_target - P_seed = i x G` for some small `i` (i.e., `i in [0, 2M]`).
5. If so, the seed and iterator are recovered, and the full private key is:
   ```
   private_key = private_key_seed + i   (mod N)
   ```

## 4. Why 2^32 is Searchable

| Parameter | Value |
|-----------|-------|
| Seed space | 2^32 = 4,294,967,296 |
| Iterator space per seed | ~2,000,000 |
| Total candidates | 2^32 |
| Single verification (naive) | ~5 ms |
| Single verification (optimised, comb method) | ~1 ms |
| 64-core search time (estimated) | ~1.6 days |

The search is embarrassingly parallel: each seed is independent.

## 5. Verification (What verify.py Does)

`verify.py` performs the forward derivation only:

```
Input: (seed, iterator)
Output: derived_address and match status

1. seed_priv = profanity_seed_to_priv(seed)     # MT19937_64 -> 4xuint64
2. full_priv = (seed_priv + iterator) mod N
3. pub = scalar_mul(full_priv, G)               # secp256k1
4. addr = keccak256(pub)[12:]                   # Ethereum address
5. match = (addr == TARGET_ADDRESS)
```

This is the **only** operation needed to confirm a recovered seed. The search itself is a simple enumeration over 2^32 seeds, accelerated with pre-computed tables.

## 6. On-Chain Validation

Once a candidate `(seed, iterator)` is found, three independent checks are performed:

1. **Address match**: `derive_address(seed, iterator) == 0x000002...080a`
2. **Transaction signature recovery**: The victim address signed multiple mainnet transactions. Using the recovered private key, we re-derive the public key and verify it matches the signature's `r` and `s` values.
3. **Nonce consistency**: The transaction nonce sequence must be monotonically increasing and match Etherscan records.

## 7. Limitations & Ethics

This methodology is **only applicable to addresses known to have been generated by Profanity**. It does not generalise to:
- Hardware wallets (entropy source is secure)
- BIP-39 mnemonic-derived keys (entropy is 128-256 bits)
- Any address generated with a CSPRNG

The brute-force engine is kept private to prevent abuse against other historical Profanity addresses that may still hold funds.
